## Название выбранного проекта

**Вариант 1. Персональный помощник «от текста до действия»** — реализован как второй продукт в репозитории OfferDesk под именем **Personal Assistant**.

---

## Ценность (для кого и зачем)

**Для кого:** один человек или небольшая команда, которая получает поток входящих мыслей, задач и поручений в виде текста («надо сделать», «идея», «позвонить», «не забыть»).

**Зачем:** всё это обычно теряется в заметках и чатах. Сервис превращает хаос входящего текста в структурированные задачи и заметки, хранит их в БД, показывает в веб-панели и **честно помечает случаи, когда нужна ручная проверка** — вместо того чтобы «уверенно» выдумывать.

---

## 3 сценария пользователя

**Сценарий 1. Создание из текста.**
Пользователь открывает `/capture`, вставляет текст («Позвонить Сергею завтра в 10:00»), нажимает «Создать». Система через LLM создаёт item типа `task`, показывает его в таблице «Последние 5» с полями: тип, приоритет, срок, источник, метка проверки.

**Сценарий 2. Витрина и выполнение.**
Пользователь открывает `/tasks`, фильтрует «В работе» / «Выполнено» / «Требует проверки» / «Все». Нажимает «Выполнено» — статус меняется на `done`.

**Сценарий 3. Ручная проверка.**
На элементе с `needs_review=true` — красный бейдж «требует проверки». Пользователь открывает карточку `/tasks/<id>`, видит сырой ввод, сырой JSON модели, причину проверки. Правит заголовок и приоритет, сохраняет — item снимается с проверки.

## Точки доступа API (список)

| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/capture` | Создать сущность: текст → item в `items` + запись в `audit_runs` |
| `GET` | `/tasks` | Витрина: список items с фильтром `?status=open\|done\|needs_review\|all` |
| `POST` | `/tasks/extract` | ИИ-обработка: текст → строгий JSON без записи в БД |
| `POST` | `/tasks/<id>/done` | Отметить выполненной |
| `GET/POST` | `/tasks/<id>/review` | Правка заголовка и приоритета, снятие `needs_review` |
| `GET` | `/tasks/<id>` | Карточка: детали + audit + сырой ввод/вывод |
| `GET` | `/journal` | Журнал `audit_runs` |

**Три ключевые точки по чеклисту:**

1. **Создать/запустить** — `POST /capture`
2. **Витрина** — `GET /tasks`
3. **ИИ-обработка** — `POST /tasks/extract`

**Аутентификация:** `X-Api-Token` / `X-API-Token` / `Authorization: Bearer` (если `FLASK_API_TOKEN` задан в `.env`). Сессия CRM тоже пускает.

## ИИ-операция

**Endpoint:** `POST /tasks/extract`

**Модель:** OpenAI `gpt-4o-mini` через `utils.chat_json`.

### Схема JSON (ItemExtraction)

```json
{
  "item_type": "task | note",
  "title": "string (≤80)",
  "body": "string",
  "priority": "low | medium | high",
  "due_date": "YYYY-MM-DD | null",
  "tags": ["string"],
  "confidence": 0.0,
  "needs_review": false,
  "review_reason": null
}
```

**Валидация:** Pydantic-модель `ItemExtraction`. Поля `item_type`, `priority`, `review_reason` — строгие enum. Поле `due_date` — ISO-дата или null.

### Температура

Извлечение и классификация: `temperature=0.2` (в `utils/chat_json`).

Принцип: низкая температура для структурирования, чтобы модель не «фантазировала».

### Когда нужна ручная проверка (`needs_review=true`)

| Причина | Условие |
|---|---|
| `LOW_CONFIDENCE` | `confidence < 0.5` |
| `INVALID_JSON` | Модель вернула невалидный JSON или упала с ошибкой |
| `SCHEMA_MISMATCH` | JSON не проходит Pydantic-валидацию |
| `AMBIGUOUS_INPUT` | Вход противоречивый или слишком общий («сделай важное», «потом разберусь») |

Что происходит при `needs_review=true`:

- элемент получает красный бейдж в `/tasks`;
- причина пишется в `audit_runs.error`;
- `audit_runs.status = needs_review`;
- пользователь открывает `/tasks/<id>/review`, правит title/priority, сохраняет.

### Безопасный ответ

Если модель не смогла разобрать вход:

- `source = "heuristic"` или `"error"`;
- `confidence = 0.0`;
- `title` = исходный текст (обрезка до 80);
- никаких выдуманных полей;
- `needs_review = true`.

## Память/контекст

**Что хранится:**

- все items в таблице `items` (постоянно);
- все запуски обработки в `audit_runs` — с сырым входом, JSON результата, статусом, длительностью.

**Как используется:**

- витрина `/tasks` фильтрует по статусу и `needs_review`;
- карточка `/tasks/<id>` показывает последний `audit_run` для контекста;
- журнал `/journal` даёт историю всех запусков.

**Что НЕ хранится:**

- персональные данные клиентов вне текста;
- ключи и секреты;
- сырые транскрибации длиннее 5000 символов (обрезаются).

**Контекст LLM:** между вызовами модели контекст не сохраняется — каждый запрос независим. Дата передаётся в каждом запросе строкой «Сегодня: YYYY-MM-DD (день недели)».

## Контроль качества

**На входе:**

- Pydantic-валидация схемы `ItemExtraction` — тип, enum, длины;
- правило `is_ambiguous()` — отсекает слишком короткие и общие входы;
- пустой текст → HTTP 400 без вызова модели.

**На выходе:**

- валидация: `material` / `financing` (для OfferDesk) приводятся к enum с fallback «не указано»;
- нормализация даты: если модель вернула год < 2025 — `needs_review=true`;
- confidence: если < 0.5 → `needs_review=true` с причиной `LOW_CONFIDENCE`;
- audit: каждый запуск пишется в `audit_runs` со всеми полями.

**Контур отказа:**

- LLM недоступен → fallback на regex/heuristic → `needs_review=true` → процесс не останавливается;
- ошибка модели → безопасный ответ без выдумок;
- Pydantic-ошибка → `SCHEMA_MISMATCH`, элемент уходит на ручную проверку.

## Мини-экономика

Одна операция вручную: ~50 минут (чтение текста, поиск в заметках, классификация, создание задачи, приоритизация).

Одна операция с системой: ~6 минут (вставка текста + проверка результата менеджером).

**Стоимость 100 операций:**

| | Вручную | С системой |
|---|---|---|
| Время | ~83 часа | ~10 часов |
| Стоимость (500 ₽/ч) | ~41 500 ₽ | ~5 000 ₽ (проверка) + ~700 ₽ (OpenAI) + ~700 ₽ (VPS) = ~6 400 ₽ |
| Экономия | | ~35 000 ₽ на 100 операций |

## Риски и меры снижения

**Риск:** OpenAI недоступен с прод-VPS (географическая блокировка).
**Мера:** fallback на regex/heuristic + зарубежный прокси (tinyproxy NL). Проверено вживую — при 403 страна система не падает.

**Риск:** Модель возвращает невалидный JSON или пропускает поля.
**Мера:** Pydantic-валидация + безопасный fallback (`needs_review=true`). 4 причины: `INVALID_JSON`, `SCHEMA_MISMATCH`, `LOW_CONFIDENCE`, `AMBIGUOUS_INPUT`.

**Риск:** Модель «уверенно» выдумывает факты (галлюцинация).
**Мера:** `temperature=0.2`, строгий промпт «не добавлять факты, которых нет», схема с enum. При `confidence < 0.5` — на ручную проверку.

**Риск:** Утечка API-ключа или ПД через логи/скриншоты.
**Мера:** `.env` в `.gitignore`, ключ не попадает в git. На VPS ключ в переменных окружения, не в коде. Скриншоты с маскировкой.

**Риск:** Потеря БД при сбое или обновлении.
**Мера:** бэкапы `deals.db` при деплое, миграции идемпотентны (`ALTER TABLE ... ADD COLUMN` в try/except), проверка `PRAGMA table_info` перед изменением.

**Риск:** Относительные даты («завтра», «до пятницы») — модель ошибается.
**Мера:** сегодняшняя дата передаётся в user prompt строкой `Сегодня: YYYY-MM-DD (день недели)`. Правило 5a в промпте: «до пятницы» = ближайшая пятница текущей недели. Пост-нормализация: год < 2025 → `needs_review`.

**Риск:** Пользователь не понимает, почему элемент «требует проверки».
**Мера:** на карточке `/tasks/<id>` явно показаны `review_reason`, источник, confidence, сырой ввод и сырой JSON модели.

## 3 строки для портфолио

**Проблема:** команда теряет входящие задачи и заметки в потоке текста — часть задач просто не доходит до выполнения.

**Решение:** веб-сервис «от текста до действия» — LLM структурирует входящий текст в задачу/заметку по строгой JSON-схеме, сохраняет в SQLite, показывает в веб-панели и помечает случаи, когда нужна ручная проверка (4 причины: `LOW_CONFIDENCE`, `INVALID_JSON`, `SCHEMA_MISMATCH`, `AMBIGUOUS_INPUT`).

**Результат:** 3 явные точки API (`/capture`, `/tasks`, `/tasks/extract`), полный аудит каждого запуска (`audit_runs` с `action`, `duration_ms`, `result_json`), 3 экрана панели (список / карточка с сырым JSON / журнал), экономия ~35 000 ₽ на 100 операциях. Работает в проде с LLM через зарубежный прокси.

## Сложности и как решал

**1. Географическая блокировка OpenAI (403 unsupported_country).**
Прод-VPS в РФ не мог напрямую обращаться к OpenAI. Поднял tinyproxy на зарубежном VPS (NL), прописал `OPENAI_PROXY` в `.env`. Проверил: curl через прокси возвращает список моделей. `POST /capture` вернул `source=llm`, `confidence=0.95`.

**2. Старый ключ и устаревший `.env` на сервере.**
После деплоя модель не отвечала, хотя ключ локально работал. Диагностика: на сервере в `.env` лежал другой ключ (не тот, что в локальном `.env`) + `OPENAI_PROXY` указывал на мёртвый прокси-хост. Заменил ключ, обновил прокси, перезапустил CRM — процесс подхватил новое окружение.

**3. `tone: "не определен"` без ё — падение Pydantic.**
Модель возвращала «не определен» (без ё), схема требовала «не определён». `POST /ingest` уходил в regex-fallback. Написал валидатор: ё снимается только для сравнения, чтобы не сломать «агрессивный» → «агрёссивный». В модель пишется канон.

**4. `material: null` от модели — падение Pydantic.**
Явный `null` не подставлялся дефолтом «не указано». Добавил `field_validator(mode="before")`, который превращает `None`/`""` в «не указано».

**5. `etalon_score` считал по «оба непустые» — методика завышала TP.**
Изначально в `run_golden_set.py` любая пара непустых значений считалась совпадением. Реальные метрики: `budget_rub` recall 0.00, а не 1.00. Патч: TP только при `exp == got`.

**6. `low_confidence` шумит на regex-сделках.**
Правило эскалации по confidence убирало эскалацию на каждой regex-сделке (regex всегда 0.3). Убрал из триггеров, оставил метрикой в audit. Добавил fallback: `legal_risk` ищется и в `objections`, и в сыром тексте — чтобы суд не терялся при regex-разборе.

**7. SSH на VPS отваливается.**
BlueTerbium периодически отвечает Connection refused на порт 2222. Решение: ControlMaster (`-o ControlMaster=auto -o ControlPath=...`) держит одну сессию, все команды выполняются внутри. Файлы доезжают с 1–2 попытки.
