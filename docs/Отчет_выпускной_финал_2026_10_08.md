## Название выбранного проекта

**Вариант 1. Персональный помощник «от текста до действия»** — реализован как второй продукт в репозитории OfferDesk под именем **Personal Assistant**.

**Дополнительно:** доработал **OfferDesk** (основной продукт репозитория — AI-квалификатор лидов для ИЖС и веб-CRM «Дом-Мастер») под требования выпускного учебного проекта. Оба продукта используют общий слой `extraction/`, единую веб-панель и одну SQLite-БД.

## Ценность (для кого и зачем)

**Для кого:**

- **Personal Assistant:** один человек или небольшая команда, которая получает поток входящих мыслей, задач и поручений в виде текста.
- **OfferDesk:** отдел продаж строительной компании ИЖС (дома из газобетона и клееного бруса), где теряется 30–40% лидов из-за медленной реакции.

**Зачем:**

- **PA:** превращает хаос входящего текста в структурированные задачи и заметки, хранит их в БД, показывает в веб-панели и **честно помечает случаи, когда нужна ручная проверка**, вместо того чтобы «уверенно» выдумывать.
- **OfferDesk:** сырой текст заявки → JSON → квалификация A/B/C → эскалация → сделка в веб-CRM: карточка, эталон протокола, PDF-КП, email. Средний чек 8 млн ₽, маржа 15% — каждый процент конверсии считается в деньгах.

## 3 сценария пользователя (вариант 1)

**Сценарий 1. Создание из текста.**
Пользователь открывает `/capture`, вставляет текст («Позвонить Сергею завтра в 10:00»), нажимает «Создать». Система через LLM создаёт item типа `task`, показывает его в таблице «Последние 5» с полями: тип, приоритет, срок, источник, метка проверки.

**Сценарий 2. Витрина и выполнение.**
Пользователь открывает `/tasks`, фильтрует «В работе» / «Выполнено» / «Требует проверки» / «Все». Нажимает «Выполнено» — статус меняется на `done`.

**Сценарий 3. Ручная проверка.**
На элементе с `needs_review=true` — красный бейдж «требует проверки». Пользователь открывает карточку `/tasks/<id>`, видит сырой ввод, сырой JSON модели, причину. Правит заголовок и приоритет, сохраняет — item снимается с проверки.

| # | Требование | Endpoint | Что делает |

## ИИ-операция

### Схема JSON

**Для Personal Assistant** — `ItemExtraction`:

```json
{
  "item_type": "task | note",
  "title": "string (≤80)",
  "body": "string",
  "priority": "low | medium | high",
  "due_date": "YYYY-MM-DD | null",
  "tags": ["string"],
  "confidence": 0.0,
  "needs_review": false,
  "review_reason": null
}
```

**Для OfferDesk** — `DealExtraction`:

```json
{
  "client": {"name": "...", "phone": "+7...", "email": "...", "telegram": "..."},
  "object": {"plot": "...", "area_m2": 150, "material": "газобетон", "floors": 1},
  "deal": {"budget_rub": 9000000, "financing": "ипотека", "start_date": "весна 2026"},
  "sales_signals": {"objections": [], "tone": "не определён", "sentiment": "нейтральный"},
  "confidence": {"overall": 0.9, "per_field": {}},
  "missing_fields": []
}
```

Обе схемы валидируются Pydantic. Enum-поля строгие.

### Температура

Извлечение и классификация: `temperature=0.2` (в `utils/chat_json`).

Принцип: низкая температура для структурирования, чтобы модель не «фантазировала».

Creative-шаг 0.7–0.9 (черновик ответа клиенту) — в roadmap; сейчас `chat_json` фиксирован на 0.2.

### Когда нужна ручная проверка (`needs_review=true`)

| Причина | Условие |
|---|---|
| `LOW_CONFIDENCE` | `confidence < 0.5` |
| `INVALID_JSON` | Модель вернула невалидный JSON или упала с ошибкой |
| `SCHEMA_MISMATCH` | JSON не проходит Pydantic-валидацию |
| `AMBIGUOUS_INPUT` | Вход противоречивый или слишком общий («сделай важное», «потом разберусь») |

Что происходит при `needs_review=true`:

- элемент получает красный бейдж в `/tasks`;
- причина пишется в `audit_runs.error`;
- `audit_runs.status = needs_review`;
- пользователь открывает `/tasks/<id>/review`, правит title/priority, сохраняет.

**Безопасный ответ:**

- `source = "heuristic"` или `"error"`;
- `confidence = 0.0`;
- `title` = исходный текст (обрезка до 80);
- никаких выдуманных полей;
- `needs_review = true`.

## Память / контекст

**Что хранится:**

- все items в таблице `items` (постоянно);
- все запуски обработки в `audit_runs` — сырой вход, JSON результата, статус, длительность;
- все сделки в `deals` (OfferDesk);
- все разборы сделок в `audit_log`.

**Как используется:**

- витрина `/tasks` фильтрует по статусу и `needs_review`;
- карточка `/tasks/<id>` показывает последний `audit_run` для контекста;
- журнал `/journal` даёт историю всех запусков.

**Что НЕ хранится:**

- персональные данные вне текста;
- ключи и секреты;
- сырые транскрибации длиннее 5000 символов (обрезаются).

**Контекст LLM:** между вызовами не сохраняется. Дата передаётся строкой `Сегодня: YYYY-MM-DD (день недели)` в user prompt.

## Контроль качества

### Валидация на входе

- Pydantic-валидация схемы `ItemExtraction` / `DealExtraction` — типы, enum, длины;
- правило `is_ambiguous()` — отсекает слишком короткие и общие входы;
- пустой текст → HTTP 400 без вызова модели.

### Валидация на выходе

- `material` / `financing` — `None` / `""` → `"не указано"` через `field_validator(mode="before")`;
- `tone` — «не определен» (без ё) принимается как «не определён»;
- дата: год < 2025 → `needs_review=true`;
- `confidence < 0.5` → `needs_review=true` с `LOW_CONFIDENCE`.

### Контур отказа

- LLM недоступен → regex/heuristic fallback → `needs_review=true` → процесс не останавливается;
- ошибка модели → безопасный ответ без выдумок;
- Pydantic-ошибка → `SCHEMA_MISMATCH`, на ручную проверку.

### Метрики (golden set, живой прогон)

| Метрика | LLM v2 | regex baseline |
|---|---|---|
| Exact `etalon_score` | 15/15 = 100% | 8/15 = 53.3% |
| `budget_rub` recall | 1.00 | 0.00 |
| `start_date` recall | 1.00 | 0.30 |
| `financing` recall | 1.00 | 0.50 |
| `area_m2` recall | 1.00 | 0.54 |

Пороги: etalon ≥ 80% → КП; 50–79% → «Недостающие данные»; < 50% → перезвонить.

## Риски и меры снижения

**Риск:** OpenAI недоступен с прод-VPS (403 `unsupported_country_region`).
**Мера:** NL-прокси (tinyproxy) на зарубежном VPS + fallback на regex/heuristic. Проверено вживую — при 403 страна система не падает.

**Риск:** Модель возвращает невалидный JSON или пропускает поля.
**Мера:** Pydantic-валидация + безопасный fallback → `needs_review=true`. 4 причины: `INVALID_JSON`, `SCHEMA_MISMATCH`, `LOW_CONFIDENCE`, `AMBIGUOUS_INPUT`.

**Риск:** Галлюцинации — модель «уверенно» выдумывает факты.
**Мера:** `temperature=0.2`, строгий промпт «не добавлять факты, которых нет», enum-поля. При `confidence < 0.5` — на ручную проверку.

**Риск:** Утечка API-ключа или ПД через логи/скриншоты.
**Мера:** `.env` в `.gitignore`, ключ не попадает в git. На VPS ключ в переменных окружения. `git log --all -p -- .env` пустой.

**Риск:** Потеря БД при сбое или обновлении.
**Мера:** бэкап `deals.db` при деплое; миграции идемпотентны (`ALTER TABLE ... ADD COLUMN` в try/except); проверка `PRAGMA table_info` перед изменением.

**Риск:** Относительные даты («завтра», «до пятницы») — модель ошибается.
**Мера:** сегодняшняя дата передаётся в user prompt строкой; правило 5a в промпте: «до пятницы» = ближайшая пятница текущей недели. Пост-нормализация: год < 2025 → `needs_review`.

**Риск:** Пользователь не понимает, почему элемент «требует проверки».
**Мера:** карточка `/tasks/<id>` показывает `review_reason`, источник, confidence, сырой ввод и сырой JSON.

## 3 строки для портфолио

**Проблема:** команда теряет входящие задачи и заметки в потоке текста — часть задач не доходит до выполнения.

**Решение:** веб-сервис «от текста до действия» — LLM структурирует входящий текст в задачу/заметку по строгой JSON-схеме, сохраняет в SQLite, показывает в веб-панели и помечает случаи, когда нужна ручная проверка (4 причины: `LOW_CONFIDENCE`, `INVALID_JSON`, `SCHEMA_MISMATCH`, `AMBIGUOUS_INPUT`).

**Результат:** 3 явные точки API (`/capture`, `/tasks`, `/tasks/extract`), полный аудит каждого запуска (`audit_runs` с `action`, `duration_ms`, `result_json`), 3 экрана панели (список / карточка с сырым JSON / журнал), экономия ~35 000 ₽ на 100 операциях, LLM работает в проде через NL-прокси.

## Сложности и как решал

**1. Геоблокировка OpenAI (403 unsupported_country).**
Прод-VPS в РФ не мог обращаться к OpenAI напрямую. Поднял tinyproxy на зарубежном VPS (NL), прописал `OPENAI_PROXY` в `.env`. Проверил: curl через прокси возвращает список моделей. `POST /capture` вернул `source=llm`, `confidence=0.95`.

**2. Старый ключ и устаревший `.env` на сервере.**
После деплоя модель не отвечала, хотя ключ локально работал. Диагностика: на сервере другой ключ + `OPENAI_PROXY` указывал на мёртвый прокси-хост. Заменил ключ, обновил прокси, перезапустил CRM — процесс подхватил новое окружение.

**3. `tone: "не определен"` без ё — падение Pydantic.**
Модель возвращала «не определен» (без ё), схема требовала «не определён». `POST /ingest` уходил в regex-fallback. Написал валидатор: ё снимается только для сравнения, чтобы не сломать «агрессивный» → «агрёссивный». В модель пишется канон.

**4. `material: null` от модели — падение Pydantic.**
Явный `null` не подставлялся дефолтом «не указано». Добавил `field_validator(mode="before")`, превращающий `None` / `""` в «не указано».

**5. `etalon_score` считал неправильно — TP на любую пару непустых.**
Изначально в `run_golden_set.py` любая пара непустых значений считалась совпадением. Реальные метрики: `budget_rub` recall 0.00, а не 1.00. Патч: TP только при `exp == got`.

**6. `low_confidence` шумит на regex-сделках.**
Правило эскалации по confidence убирало эскалацию на каждой regex-сделке. Убрал из триггеров, оставил метрикой в audit. Добавил fallback: `legal_risk` ищется и в `objections`, и в сыром тексте.

**7. SSH на VPS отваливается (BlueTerbium, порт 2222).**
Периодически Connection refused. Решение: ControlMaster (`-o ControlMaster=auto -o ControlPath=...`) держит одну сессию, все команды — внутри.

4. **Live-дашборд качества** — precision/recall, % эскалаций, распределение A/B/C поверх `audit_runs` и `audit_log`.
5. **WhatsApp + creative-шаг LLM (temperature 0.7)** — отдельный вызов для черновика ответа клиенту.
6. **Платные каналы → CPQL** — атрибуция источника, выгрузка расходов из рекламных кабинетов, метрика cost per qualified lead.
7. **Дашборд PA** — счётчики items, распределение task/note, % `needs_review`.
8. **`seed_items.py`** — заполнить БД демо-данными для показа.
9. **Видео-демо** — записать 3–5 минут с 3 сценариями.
