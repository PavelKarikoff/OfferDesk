## 1. Почему я отошёл от первоначального задания

Формулировка ДЗ — учебный inbox поддержки: один `POST /triage`, четыре категории (billing / support / complaint / other), черновик ответа в JSON, флаг эскалации, таблица `tickets`.

Я **сознательно** не стал делать учебный тикет-классификатор. Причина не в том, что буква задания «не понравилась», а в том, что у меня есть **реальный клиент из строительного бизнеса** («Дом-Мастер» и смежный контур домов из клееного бруса). Его отдел продаж каждый день решает другую задачу:

> после телефонного звонка менеджер вручную собирает данные из протокола и пишет коммерческое предложение. На это уходит время, часть полей теряется, клиенту уходит неполный или «сырой» документ.

Это живая операционка ОП, а не абстрактный саппорт. Четыре корзины «биллинг / жалоба / поддержка / прочее» не отвечают на вопрос менеджера: **можно ли уже считать КП, или сначала нужно доспросить клиента**.

Поэтому я взял реальную бизнес-проблему клиента и построил вокруг неё сервис. Учебный `/triage` в репозитории остался как черновик буквы ДЗ — **на проверку его не выставляю**. Сдаю рабочее место менеджера.

Прошу оценивать работу как **практику AI-автоматизации на реальном процессе**, а не как совпадение имён эндпоинтов 1:1.

## 2. Что сдаю

Сдаю **веб-сервис для менеджера отдела продаж**, не чат-бот.

OfferDesk — рабочее место в браузере. После звонка менеджер создаёт сделку, загружает транскрибацию (текст или файл), система сверяет её с эталоном протокола и либо генерирует коммерческое предложение в PDF, либо показывает, каких данных не хватает, и даёт готовые вопросы клиенту. Утверждённое КП уходит клиенту по **email** (основной канал) или в Telegram, если клиент привязал чат.

Telegram в проекте — канал доставки, не интерфейс продукта.

Публичная проверка: CRM по ссылке выше; health: `GET http://194.67.103.144:5001/health`.

## 3. Как критерии практики всё равно закрыты

Идея ДЗ сохранена: принять обращение → оценить уверенность → либо черновик ответа, либо эскалация человеку → записать аудит → не хранить секреты в коде. Предметная область другая.

| Идея ДЗ | Как сделано в OfferDesk |
|--------|-------------------------|
| Обработать обращение | Транскрибация звонка → сделка в CRM |
| Классификация | Соответствие эталону: готово к КП / нужна доработка |
| Уверенность | % заполнения полей (порог КП — 80%) |
| Эскалация человеку | Статус «неполные данные», нет кнопки КП, скрипт вопросов |
| Черновик ответа | Вопросы по пробелам **или** PDF коммерческого предложения |
| Не выдумывать | Парсер + эталон; при дырах — эскалация, не «уверенное КП» |
| Аудит в SQLite | Таблица `deals` + журнал `action_log` |
| Секреты в env | Ключи только в `.env`, не в git |
| Сбой LLM / сети | Повтор / шаблонное КП без AI; менеджер не видит traceback |
| Развёртывание | Публичный URL на VPS, systemd, health-check |

Стек: Python 3.11, Flask, OpenAI, SQLite, Docker, OpenAPI. Дополнительно: WeasyPrint (PDF), SMTP, Telegram как доставка.

Учебный модуль `POST /triage` (`app/routes/triage.py`, `run_triage.py`) в коде есть. Если понадобится контракт 1:1 — могу поднять отдельно и прислать curl. Основной контур на порту 5001 — CRM.

## 4. Как проверить сдачу

1. Открыть http://194.67.103.144:5001 — логин выдаёт администратор (для проверки могу выдать учебную учётку).  
2. `GET /health` → сервис жив.  
3. Новая сделка → вставить протокол → смотреть % эталона: при ≥ 80% «Сгенерировать КП», иначе «Недостающие данные».  
4. Учебные тексты в репозитории: `knowledge_base/demo_protocol_1.md` (≈100%) и `demo_protocol_2.md` (≈43%). На боевой CRM **не** нажимать «Загрузить демо» — это сотрёт сделки.  
5. GitHub: https://github.com/PavelKarikoff/OfferDesk — README описывает продукт как веб-CRM, не бот.

## 5. Просьба к приёмке

Прошу засчитать работу как **MVP обработки обращений отдела продаж** на реальной задаче строительного клиента, с публичным развёртыванием.

Расхождение с чеклистом (`POST /triage`, четыре категории, таблица `tickets`) — не недоделка и не «не успел сделать учебный вариант». Это выбор: вместо синтетического inbox взять процесс, которым менеджер ОП пользуется после звонка.

Критерии практики (валидация входа, рамки для LLM, эскалация при сомнении, аудит, секреты в env, доступная проверка) в сдаваемом сервисе есть.
